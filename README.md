# TRACE Continual Learning: Diffusion vs Autoregressive LMs

This repo compares **catastrophic forgetting** behavior between **diffusion language models (DLMs)** and **autoregressive LLMs (AR LMs)** under **continual fine-tuning** on the [TRACE benchmark](https://github.com/BeyonderXX/TRACE).

> Research question: when the same sequence of tasks is learned sequentially, do diffusion LMs forget previously learned tasks more or less severely than AR LMs, and why?

## Models compared
| Family | Models |
| --- | --- |
| Diffusion LMs | Dream-7B, LLaDA-8B (masked / denoising generation) |
| Autoregressive LMs | LLaMA-3-8B, Qwen2.5-7B (left-to-right causal generation) |

All four backbones share the same training entry point (`training/main.py`) and the same task stream. LoRA adapters are the default for parameter-efficient continual fine-tuning so cross-architecture comparisons stay controlled.

## TRACE task stream
The sequential stream covers 8 tasks across domains and languages (learning order, left to right):

`C-STANCE` → `FOMC` → `MeetingBank` → `Py150` → `ScienceQA` → `NumGLUE-cm` → `NumGLUE-ds` → `20Minuten`

| # | Task | Type | Metric |
| --- | --- | --- | --- |
| 1 | C-STANCE    | Chinese stance detection                       | Accuracy        |
| 2 | FOMC        | Financial sentiment / policy classification    | Accuracy        |
| 3 | MeetingBank | Meeting summarization                          | ROUGE           |
| 4 | Py150       | Python code completion                         | Code similarity |
| 5 | ScienceQA   | Multiple-choice science QA (text-only)         | Accuracy        |
| 6 | NumGLUE-cm  | Numerical reasoning (commonsense math)         | Exact match     |
| 7 | NumGLUE-ds  | Numerical reasoning (data science)             | Exact match     |
| 8 | 20Minuten   | German summarization                           | ROUGE / SARI    |

> Note: training scripts use **`FOMC_shuffled`** instead of raw `FOMC` — a per-sample ABC-permuted variant generated by `preprocess/shuffle_fomc_labels.py`, to break the strong C-label bias of the original FOMC split (where ~49% of labels are `C`). The data is generated under each `LLM-CL-Benchmark_<size>/FOMC_shuffled/` directory; task dispatch (eval / collator / block-length tables) automatically normalizes the name back to `FOMC`.

## Repository layout
```
training/        # Continual fine-tuning entry point (main.py, params.py)
model/           # Backbone wrappers + LoRA; separate generation paths
                 #   dream_generate.py / llada_generate.py for diffusion
                 #   base_model.py for AR
evaluations/     # Per-task evaluators (eval_<task>.py) + eval_with_gpt_api.py
inference/       # Inference entry point (infer_single.py)
scripts/         # 3 training configs × 4 backbones = 12 one-shot pipelines
                 #   run_{dream_lora, llada_8b, llama_8b, qwen_7b}_5000_e{5,10,15}.sh
                 #   Each: train + full test-set infer; configs differ on epochs / eval / batch
setup_env.sh     # One-shot installer (creates conda env + pip install)
utils/           # Tokenization, dataset, collator, LoRA, DS config, CL metrics
preprocess/      # Data preprocessing
                 #   shuffle_fomc_labels.py — per-sample ABC permutation (break C-bias)
                 #   preprocess_ssr.py      — SSR benchmark formatting
sari/            # Standalone SARI metric implementation

calculate_metrics.py             # Aggregate AP / BWT / FWT across rounds
metrics.py                       # Continual-learning metric definitions
```

## Continual-learning metrics
- **AP** — Average Performance after learning all tasks.
- **BWT** — Backward Transfer (signed forgetting on prior tasks).
- **FWT** — Forward Transfer (zero-shot benefit on future tasks).

## Installation

One-shot setup (creates `trace_env` conda env and pip-installs everything):
```bash
bash setup_env.sh
conda activate trace_env
```

Core stack: **torch 2.8 + CUDA 12.8**, transformers 4.44, tokenizers 0.19, deepspeed 0.18, peft 0.18, accelerate 1.13, datasets 4.8. Full pinned list in `requirements.txt`.

> Python 3.10–3.12. The `torch==2.8.0+cu128` wheel comes from `https://download.pytorch.org/whl/cu128` (already configured as an `--extra-index-url` in `requirements.txt`). If you prefer to skip conda, just run `pip install -r requirements.txt` inside any clean venv.

### Auto-download

You **don't need to manually download anything** — both TRACE data and model weights are pulled lazily:

- `bash setup_env.sh` → at the end, downloads TRACE benchmark from **Google Drive** (via `gdown`) and unzips to `./data/TRACE-Benchmark/` (idempotent).
- `bash scripts/run_<model>_5000_e<N>.sh` → at the start, `huggingface-cli download` the model to `./models/<name>/` if `config.json` is missing (idempotent).

## Quick start

All scripts assume you run them **from the repo root** (so the relative `./models/` and `./data/` paths resolve).

Each `run_<model>_5000_e<N>.sh` is a **one-shot pipeline**: it trains all 8 tasks sequentially **and** runs full test-set inference at the end.

### Three training configurations

All 3 configs share `bs=2`, `grad_accum=8` (effective batch = 16). The only differences are epoch count and whether in-training eval is enabled:

| Suffix | Epochs/task | In-training eval |
| --- | --- | --- |
| `_e5`  | 5  | none |
| `_e10` | 10 | none |
| `_e15` | 15 | every 2 epochs (50 dev samples → `epoch_eval.json`) |

Everything else is identical across all 3 configs and all 4 models: `lr=1e-4`, `seed=1234`, `bf16`, `zero_stage=2`, `max_prompt_len=1024`, `max_ans_len=512`, `inference_batch=4`, deterministic greedy inference (`temperature=0.0`). Diffusion variants use `sampling_steps=0` (auto-scaled to `max_ans_len`); Dream uses `dream_alg=maskgit_plus`, LLaDA uses `remasking_strategy=low_confidence`. Architectural exceptions: LLaDA skips `--gradient_checkpointing`; diffusion backbones add `--fix_eos`.

### Run a single (model, config) end-to-end

```bash
# Config A — 5 epoch, no in-training eval (baseline)
bash scripts/run_dream_lora_5000_e5.sh
bash scripts/run_llada_8b_5000_e5.sh
bash scripts/run_llama_8b_5000_e5.sh
bash scripts/run_qwen_7b_5000_e5.sh

# Config B — 10 epoch, no in-training eval
bash scripts/run_dream_lora_5000_e10.sh
# ... (llada / llama / qwen variants)

# Config C — 15 epoch, eval every 2 epochs (only config with in-training eval)
bash scripts/run_dream_lora_5000_e15.sh
# ... (llada / llama / qwen variants)
```

Each script does:
1. **Train** — writes adapters to `outputs_<model>_5000_e<N>/lora_<size>/{0..7}/` (one per task) plus `train_full.log`. Only `_e15` also writes convergence metrics to `epoch_eval.json` (at epochs 2, 4, 6, …, 14).
2. **Infer** — full test-set pass on all rounds, writes `outputs_<model>_5000_e<N>/lora_<size>/predictions/results-<round>-<task_idx>-<task>.json`.

Per-model output directory structure (config `_e15`):
```
outputs_<model>_5000_e<N>/lora_<size>/
├── {0..7}/                                          task-end LoRA adapters (1 per task)
├── train_full.log
├── epoch_eval.json                                  ★ convergence summary {task: {epoch: metrics}}
├── epoch_predictions/                               per-epoch dev predictions, grouped by task
│   ├── 0/                                           task 0 (C-STANCE) — 7 files (epoch 1,3,5,7,9,11,13)
│   │   └── results-0-0-C-STANCE-ep<N>.json
│   ├── 1/                                           task 1 (FOMC_shuffled) — 7 files
│   │   └── results-1-1-FOMC_shuffled-ep<N>.json
│   ├── ...
│   └── 7/                                           task 7 (20Minuten) — 7 files
└── predictions/                                     full test-set predictions (Phase 2)
    └── results-<round>-<task_idx>-<task>.json
```

### Aggregate final TRACE metrics (AP / BWT / FWT)

```bash
python calculate_metrics.py --output_dir outputs_<model>_5000_e<N>
```

For free-form generation tasks (summarization, code), the LLM-judge path lives in `evaluations/eval_with_gpt_api.py` (requires `OPENAI_API_KEY`).

## Conventions
- Generation paths for diffusion (`model/dream_generate.py`, `model/llada_generate.py`) stay isolated from the AR path — diffusion-specific flags like `--sampling_steps`, `--dream_alg`, `--diffusion_dynamic_canvas` live there.
- LoRA is the default adapter; full fine-tuning is possible but usually not the comparison of interest.
- Output directories follow `outputs_<model>_<steps>/` so the metrics-aggregation scripts can discover runs by pattern.
- LLaDA training currently **must not** use `--gradient_checkpointing` (see existing scripts for the working flag set).
